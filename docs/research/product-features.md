# Smart-CRM — Consolidated Product Feature Research

**Author:** Product Research lead (consolidation of 6 focus-area briefs)
**Date:** 2026-06-20
**Source briefs:** Records & data model · Pipeline & deals · Activities & calendar · Reporting & dashboards · Collaboration · Onboarding/UX/search
**Companion doc:** platform/infra dependencies are tracked in `docs/research/backend-design.md` (cron runner, email provider, full-text search, event logging). Product features that need platform work are cross-referenced to it below.

This report consolidates the six product-research briefs into one prioritized view. It de-duplicates the many intentional overlaps between briefs (notably saved views, notifications, bulk actions, stage-history, and forecasting), maps every distinct idea onto Smart-CRM's actual schema / server-action / UI patterns, and tiers each by effort and strategic value. The goal is a single roadmap the team can sequence against, with quick wins called out so we can ship visible value while the larger platform investments land.

## Current product surface (recap)

Smart-CRM today is a clean, multi-tenant Next.js 15 app (App Router + RSC + server actions, Prisma/Postgres, NextAuth v5, Tailwind/shadcn). Every business table carries `orgId` and every server action funnels through `requireOrg()` (`src/lib/tenant.ts`) with optional `requireRole()` RBAC (`src/lib/rbac.ts`, OWNER>ADMIN>MEMBER), Zod validation, and a uniform `ActionResult` return (`src/lib/action-result.ts`). The shipped surface is: **Contacts** (with tags + CSV export, the most advanced list page at `src/app/(app)/contacts/page.tsx`), **Companies**, **Deals** as a single @dnd-kit **Kanban** (`src/app/(app)/deals/kanban.tsx`, one pipeline per org), **Activities** (a flat list of TASK/CALL/MEETING/NOTE with create/toggle/delete only — no edit), a hardcoded **Dashboard** (4 KPI stats + one recharts pipeline-by-stage bar + "Up next"), a global **⌘K** command palette (`src/components/command-palette.tsx`, search-and-navigate only), and **Settings/RBAC** (membership management). Notably absent and recurring across briefs: custom fields, a leads object, saved/configurable views, notifications, comments, stage history, forecasting, a calendar, and any time-triggered job runner or email provider.

## Themed sections

### Records & data model

**Custom fields** are the keystone of this entire brief and arguably the whole report — the single biggest gap vs HubSpot/Pipedrive/Zoho/Salesforce, and the prerequisite for validation rules, configurable views/columns, layouts, and custom objects. The recommended shape is a `CustomFieldDefinition` table plus a typed-column EAV `CustomFieldValue` (keeping filtering/sorting indexable, matching the repo's `(orgId, …)` index convention), with a lighter `customFields Json?` column acceptable for v1. Admin CRUD lives in a new `custom-fields.ts` gated exactly like `updateOrgName` in `src/server/actions/org.ts`, and `createContact`/`updateContact` extend to persist a `customFields` payload validated by a dynamically built Zod schema. **Field validation & required rules** ride directly on the same definitions (adding `required`/`unique`/`min`/`max`/`pattern`), composing the validator at runtime and reusing the existing `fail("Invalid input", fieldErrors)` → form-error channel in `src/lib/action-result.ts`.

**A Leads object + Lead Inbox + convert-to-contact** is the clearest competitive differentiator — it turns Smart-CRM from a contact database into a sales CRM. The `Lead` model deliberately mirrors `Deal`'s owner/value/status shape so it slots into existing conventions, and the transactional `convertLead()` (creating Contact/Company/Deal in one `db.$transaction`) reuses the pattern already in `inviteMember` (`org.ts`). **Lifecycle stage** is a high-value segmentation primitive at modest effort: clone the `PipelineStage` table into a configurable `LifecycleStage` with a `setContactLifecycleStage` action mirroring `moveDealToStage`.

**Data-quality features** matter the moment real data arrives. **Guided CSV import with field mapping** is the obvious counterpart to the existing export (`contacts/export/route.ts` + `src/lib/csv.ts`) and the primary on-ramp for real data; **duplicate detection & merge** protects every other feature's value, with a transactional `mergeContacts()` that re-points `Deal`/`Activity`/`ContactTag` relations (safe because the FKs are already nullable `onDelete: SetNull`). **Record source tracking** is a trivial additive column set that the importer stamps automatically. The strategic bets here — **configurable record layouts** (drag fields into sections via the existing @dnd-kit) and **custom objects** (a metadata engine reusing custom-field storage) — are the moves that make Smart-CRM a *platform*, but only after fields/views/layouts ship.

### Pipeline & deals

**Multiple pipelines** is the foundational gap: today `PipelineStage` has `@@unique([orgId, name])` — exactly one stage set per org. Adding a `Pipeline` model, `pipelineId` on `PipelineStage`+`Deal`, and changing stage uniqueness to `@@unique([pipelineId, name])` unlocks per-pipeline probability, forecasting, and quotas. The migration + backfill (one "Default" pipeline per org) is the bulk of the work; the UI is a header `<Select>` plus a same-pipeline guard in `moveDealToStage` (which today only checks `orgId`). It's also the moment to de-duplicate the `DEFAULT_STAGES` literal currently copied in both `auth.ts` and `seed.ts`.

**Stage probability + weighted value → forecast** is the revenue thread. Small additions (`probability Int?` on `PipelineStage` and `Deal`) immediately upgrade the Kanban (a weighted reducer beside the raw `totals` in `kanban.tsx`) and the dashboard, then power a Pipedrive-style **revenue forecast board** (`deals/forecast/page.tsx` reusing the @dnd-kit scaffolding, columns keyed by `closeDate` month) and a **forecast report**. **Stage-change history + automation** introduces `DealStageEvent` (the same substrate the reporting brief calls its analytics foundation — see below) by instrumenting the four deal mutations inside a transaction, and layers lightweight automation (require fields to advance, auto-create a follow-up `Activity`).

Two low-cost, high-signal Pipedrive-signature behaviors stand out as quick wins: **rotting indicators** ride entirely on the existing `Deal.updatedAt` with a pure, Vitest-friendly `isRotting()` helper and a red badge in `kanban.tsx`; **required win/loss reasons** need only a small `CloseReason` model and a tweak to `setDealStatus` (switching `updateMany`→`findFirst`+`update` to validate the reason), and they feed the loss-analysis reporting managers ask for first. The strategic bets — **products/line-items** (deal `value` rolls up from items, kept as a cached sum so the Kanban/dashboard keep working), **quotes/proposals** (public token-scoped route outside the `(app)` auth group), and **recurring products/MRR-ARR** — form a natural chain, with products as the hard prerequisite for the other two. **Quotas & targets** overlap heavily with the reporting brief's Goals (merged in the table).

### Activities & calendar

The cheapest, highest-leverage move is **editable activities + per-record timeline**, done together. The current actions support create/toggle/delete but **no edit** — adding `updateActivity` (mirroring `createActivity`'s Zod + an ownership `findFirst({where:{id,orgId}})`) and `rescheduleActivity` unblocks the calendar, reminders, and recurrence. The **per-record activity timeline** adds one column — `Activity.companyId` (+index) — so company pages finally get a timeline and a contact's company rolls up its people's activity, rendered by a shared `<ActivityTimeline>` (grouped Today/Yesterday/This week, type icons) reused on contact/deal/company. **Call/meeting outcomes** (`Activity.outcome`) and **"My Day" buckets** (derived from `dueAt`/`completedAt`, no schema) round out the quick wins.

The **calendar / agenda view** is the single most visible missing feature vs Pipedrive/Salesforce, and the data (`dueAt`) is already there — build a client grid with `date-fns` (present) and reuse @dnd-kit for drag-to-reschedule. **Reminders and recurring tasks** are best built together because they share the **time-triggered job runner that does not exist today** — a Vercel Cron + authenticated `src/app/api/cron/*` route (tracked in `docs/research/backend-design.md`). That same cron, plus an **email provider** (also absent), is the gating dependency for the strategic bets: **sales sequences** (the flagship cadence engine, whose task steps create `Activity` rows to stay in the unified timeline), **email send + open/click tracking** (public pixel/redirect routes; note `Account` already persists OAuth tokens for a connected-inbox approach), **two-way calendar sync** (extend the OAuth scopes already stored in NextAuth's `Account`), and the **meeting scheduler** (public `(public)/book/[slug]` surface). **Custom activity types** is a Core enum→table migration that ripples through the Zod schema, the form `<select>`, and badge rendering.

### Reporting & dashboards

The brief's clearest message: there is **no stage-transition history** on `Deal` (only the current `stageId` + `updatedAt`), so funnel conversion, time-in-stage, velocity, and stage-entry goals are impossible to compute accurately. **The `DealStageEvent` log is therefore the foundation** — cheap to add now by instrumenting the four deal mutations, painful to retrofit later because history can't be reconstructed. (This is the same table the pipeline brief proposes for stage history; build it once.) A cross-cutting fix rides along: move KPI aggregation off "load all rows + JS `reduce()`" in `dashboard/page.tsx` to Prisma `groupBy`/`aggregate`.

On that substrate sit the reports: a **funnel & conversion report** (`groupBy(['stageId'])`, v2 using events), **sales velocity & time-in-stage**, an **activity/productivity report** (free on the existing `[orgId,dueAt]`/`[orgId,completedAt]` indexes), and a **sales leaderboard** (`groupBy(['ownerId'])`, no schema — a quick win on existing data). **Goals & targets** is the biggest *visible* gap vs Pipedrive/Zoho and reuses the same per-owner aggregation as the leaderboard (two features for ~one backend's effort); team scope is blocked on a future Team model. The platform plays are **configurable custom dashboards** (`Dashboard` + `DashboardWidget` grid, refactoring `dashboard/page.tsx` into a `type`→component renderer) and a **whitelisted report builder** whose `runReport()` executor becomes the engine that dashboards and exports both call. **CSV export** of any report is near-free (clone `contacts/export/route.ts`); **scheduled/emailed reports** and **KPI snapshot/trend history** both need the cron + email infra from `docs/research/backend-design.md`. **Dashboard filters & drill-downs** turn static charts into navigation by adding shared `where` clauses and routing chart clicks to filtered list pages.

### Collaboration

The collaboration surface is essentially empty — which is the opportunity, since every competitor treats record comments + @mentions + a notification center + a per-record timeline + follow as **table stakes, not premium**. The foundation is **record comments**: a polymorphic `Comment {entityType, entityId, body}` (a `CommentEntity` enum reused across Comment/RecordEvent/Follow/SavedView) dropped into the record-detail `<aside>` that `deals/[id]/page.tsx` already provides. **@Mentions** add a `Mention` join row with `@[Name](userId)` tokens and member-scoped autocomplete. **The in-app notification center** introduces a shared `AppHeader` (currently there is none — this single component also unblocks mobile nav) with a bell, dropdown, and `/notifications` page; poll-on-focus keeps it inside the current stack with no websocket infra. The **notification wiring** is then mostly logic — `notify()` calls inside `createComment`, deduped by updating an existing unread row.

A second pillar is the **per-record change feed** — an append-only `RecordEvent {field, oldValue, newValue, actorId}` written by a `logEvent()` helper + a shared `diffFields()` in the existing deal/contact/company mutations (distinct from the business-`Activity` object). It powers a unified `<RecordFeed>` and, almost for free, the **org-wide activity feed** (a different query over the same table's `@@index([orgId, createdAt])`). **Follow/subscribe** and **multi-owner/collaborators & handoff** layer on top — the latter fixes a real gap (`Contact`/`Company` have no `ownerId` today) and makes `removeMember` safe instead of orphaning owned deals via `SetNull`. **Saved & shared views** appears here too (merged into one feature in the table). The heavier, paid-tier items — **notification preferences + email digests** and **automated assignment routing** — both depend on infra/earlier layers, and **mobile/responsive** is a no-schema UI investment whose `AppHeader` is shared with the notification center.

### Onboarding, UX & search

The UX skeleton is clean but thin, and several wins are nearly free. **Dark mode is ~90% built and 0% reachable**: `next-themes` is installed-but-unused, the full `.dark` palette already exists in `globals.css`, and the root layout already sets `suppressHydrationWarning` — only a `ThemeProvider` + toggle are missing (an S-effort credibility win). A **first-run onboarding checklist** (3–5 data-driven steps off cheap `count` queries, dismissed via a flag or cookie) and **richer empty states with sample-data seeding** (factor `seed.ts`'s record logic into a `sample-data.ts` that writes to the caller's `orgId`) directly attack the cold-start blank slate new orgs hit today.

The backbone investment is **advanced multi-condition filters → saved views**: generalize the conditional `where` already in `contacts/page.tsx` into a typed, whitelisted filter DSL (`src/lib/filters.ts`) and persist filter+column+sort configs as `SavedView` rows, applied uniformly to Companies and Activities (which have zero filtering today). The **⌘K palette → actions** upgrade turns the existing search-only `command-palette.tsx` into a Linear/Notion-style command surface via an action registry, and is the connective tissue for **keyboard shortcuts** (`g c`/`g d`, `?` cheat-sheet) and theming. **Smarter fuzzy + scoped search** extends `search.ts` with Postgres `pg_trgm`/GIN (a migration tracked in `docs/research/backend-design.md`), broader coverage (activities/phone/notes), scope chips, and recents. **Bulk actions** (with per-id `orgId` re-checks — security-critical in multi-tenant) pair with filters/views. The longer-horizon items are an **accessibility (WCAG AA) program** (fixes land in shared primitives so they propagate cheaply; unlocks enterprise/VPAT deals), **i18n/l10n** (greenfield `next-intl`; main cost is one-time copy extraction across ~30 files — sequence late so strings are authored translation-ready), and **display density presets**.

## Top 10 product features (prioritized)

1. **Custom fields** (L, Core) — the single highest-leverage investment and the named #1 data-model gap; the foundation for validation, configurable views/columns, layouts, and custom objects. Nothing else reaches full value without it.
2. **Saved & shared views + advanced filters** (M+L, Core) — the daily-driver UX that moves Smart-CRM from "toy list" to platform; one view engine reused across Contacts/Companies/Deals/Activities, riding the existing `searchParams` pattern.
3. **Deal stage-event log** (M, Core) — cheap to add now, painful to retrofit; the substrate for funnel-flow, velocity/time-in-stage, stage-entry goals, *and* the deal stage-history timeline. Pure backend.
4. **Record comments + @mentions** (M+M, Core) — the highest-impact table-stakes collaboration gap (Smart-CRM has none); slots into the existing record `<aside>` and `ActionResult` patterns.
5. **In-app notification center** (M, Core) — a mention/assignment is worthless if unseen; the shared `AppHeader` built here also unblocks mobile nav. Poll-on-focus, no new infra.
6. **Multiple pipelines** (M, Core) — the foundational pipeline gap vs every competitor; unlocks per-pipeline probability, forecasting, and quotas. Mostly a migration + backfill.
7. **Calendar / agenda view + editable activities** (M+S, Core) — the most visible missing CRM surface, on data (`dueAt`) that already exists; `updateActivity` is a tiny but blocking prerequisite for reminders and recurrence.
8. **Guided CSV import + duplicate detection/merge** (M+M, Core) — the primary on-ramp for real data plus the dedupe that protects every other feature's value; the obvious counterpart to existing export.
9. **Leads object + Lead Inbox + convert** (L, Strategic Bet) — the clearest differentiator that turns a contact database into a real sales CRM; fits the `Deal`-style schema and transactional-action patterns cleanly.
10. **Configurable custom dashboards** (L, Strategic Bet) — the flagship platform capability reframing Smart-CRM from "a fixed dashboard" to "a reporting platform"; sequence after a few widget-producing reports (funnel, leaderboard, activity) exist.

*Balance:* items 1–8 are Core/foundational (mix of M and a couple of L) and several carry quick wins inside them (editable activities, leaderboard, CSV export); items 9–10 are the strategic bets that define the product's ceiling. The two recurring platform prerequisites — a **cron runner** and an **email provider** (both absent today, tracked in `docs/research/backend-design.md`) — gate the next tier of strategic bets (sequences, calendar sync, scheduled reports, email digests) and should be sequenced deliberately once the Core layer lands.
